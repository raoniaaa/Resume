01 / OVERVIEW

先获得真实数据，再允许 Agent 做分析。

金融场景对事实准确性和来源可追溯要求很高。StockGenie 把行情、财报、行业排行与历史 K 线工具接入多 Agent 辩论，并在执行前、工具格式、输出内容和前端渲染四个层面建立防护，避免模型跳过数据直接给出看似专业的结论。

COORDINATION

单模型视角有限

研究员只整理客观数据，多方和空方基于相同证据并行论证，投研总监负责评估论据并输出最终结构化摘要。

TRUTH

模型容易凭空分析

requireToolFirst 协议主动拦截未调用数据工具的分析请求，形成“查询真实数据—逻辑推理—专业分析”的强制顺序。

FORMAT

工具格式不稳定

通过 XML 工具协议、格式拦截器和多轮纠错重试，过滤裸 JSON、Markdown 代码块和非规范调用。

STREAM

长链路需要渐进反馈

WebFlux 与虚拟线程调度多 Agent 推理，并把执行阶段映射为 StreamEvent，让前端持续展示进度和结果。

02 / RESPONSIBILITY

重点负责多 Agent 编排、RAG 和可靠性防线。

01

四角色辩论协作

定义 Researcher、Bull Analyst、Bear Analyst 和 Director 的职责边界，组织客观数据、多空论证与共识决策。

02

金融 RAG 管线

接入 Supabase pgvector 与 BAAI/bge-m3，完成段落分片、文件名元数据透传、动态阈值和启动预检。

03

工具调用协议

设计 XML 调用格式与防御性重试，在模型格式违规时注入错误反馈并回滚重试。

04

输出审计与渲染防护

拦截虚假占位符和低质量 ASCII 走势图，避免不可信财务数据下发及 Markdown 布局破裂。

03 / ARCHITECTURE

数据层、辩论层与决策层各司其职。

用户请求先由研究员触发真实工具和 RAG 检索，形成共享证据。多空分析师只基于该证据并行论证，最终由总监聚合并通过 JSON 校验输出；全链路事件经 SSE 逐步送达前端。

04 / CORE MODULES

六道工程机制约束 Agent 行为。

01

辩论式共识

通过角色剥离降低单一模型偏见：研究员不表达多空倾向，分析师使用对立视角，总监评估逻辑而非简单投票。

02

自检式 RAG 导入

服务启动先检测向量数据，存在则跳过导入，减少频繁重启和 CI/CD 中的重复向量模型调用。

03

来源增强分片

DocumentByParagraphSplitter 使用 1000/200 策略，并将物理文件名注入分片前缀，提高知识归属感和来源追溯。

04

XML 工具协议

强制模型输出标准 function 标签，格式违规时捕获并追加针对性错误提示，在最大迭代范围内自动纠错。

05

数据幻觉审计

执行与输出双层检测 XXX、0000、000.0 等非法占位符，命中后阻断下发并引导模型重新生成。

06

响应式事件流

Flux/Mono 与虚拟线程调度 Agent 链路，把数据收集、论证、决策和校验错误统一映射为结构化事件。

05 / ENGINEERING DECISIONS

可靠性优先于“模型自由发挥”。

Tool-First 强约束

仅靠 Prompt 提醒更灵活，但模型仍可能绕过真实数据。

在执行服务主动拦截无工具分析，牺牲少量自由度换取事实基础。

XML 调用协议

直接接受多种输出格式兼容性高，但解析和错误边界不稳定。

统一 XML 包装并配合自动重试，使工具调用有明确、可验证的协议。

启动预检

每次启动重建向量数据最简单。

检测 pgvector 状态后决定是否导入，减少重复计费和发布等待时间。

服务端流式清洗

让前端自行容错会分散逻辑。

在后端剥离非法占位符与 ASCII 图，使所有客户端获得一致、可渲染的内容。

06 / OUTCOME

形成从真实数据到可读决策的完整闭环。

4 Roles

研究、对立论证与总监决策职责清晰分离。

Tool-First

End-to-End

RAG、工具、辩论、审计和流式渲染统一在一条工程链路中。
