01 / OVERVIEW

评估的不只是答案，而是答案背后的信源分布。

GEO 监控通常依赖开放 API，但真实用户使用的 C 端 App 可能采用完全不同的检索生态。项目以豆包 App 为目标场景，识别其对短视频信源的依赖，通过多源补偿检索、动态 Query 和端到端指标拟合真实用户看到的结果。

GAP

API 与 App 不同源

开放 API 缺少部分短视频生态结果，即使模型和 Prompt 接近，最终引用与品牌提及仍会产生显著差异。

QUERY

固定问题缺乏真实性

静态测试 Query 无法覆盖真实用户口语表达和意图变化，需要根据监控目标持续生成并做质量筛选。

EVALUATION

单一相似度不够

答案文字相似并不等同于信源一致，因此同时评价链接重合、语义相似和品牌实体识别。

DRIFT

目标平台持续变化

App 算法和 Prompt 会更新，静态 Agent 会随时间失效，需要把真实 Query-Response 当作动态基准持续校准。

02 / RESPONSIBILITY

从 Query 生成到漂移校准，设计完整评估闭环。

01

跨信源差异分析

分析火山引擎 API 与豆包 App 的检索差异，定位短视频信源缺失，并设计视频摘要与图文转化内容的补偿策略。

02

动态 Query 与质量门控

使用 DeepSeek 生成符合 C 端用户表达习惯的候选 Query，引入 LLM-as-a-Judge 和 Reflexion 重写循环。

03

LangGraph 状态机

组织 Query 生成、并发检索、清洗、评估和条件回退，使用 Checkpoint 支持断点续传和人工介入。

04

动态 Ground Truth

持续采集真实客户端 Query-Response，自动检测结果差异与算法漂移，并触发 Prompt 与检索策略调整。

03 / ARCHITECTURE

生成、判断、检索、评估，再回到校准。

主链路先保证问题质量，再进入多源并发检索。结果清洗后与真实 App Ground Truth 进行三维对比，漂移检测把误差反馈给 Query、Prompt 与检索策略。

04 / CORE MODULES

六个组件让拟合过程可解释、可迭代。

01

Dynamic Query Generator

根据品牌、监控目标和用户画像生成自然、口语化的候选问题，避免只围绕内部运营关键词进行测试。

02

Judge + Reflexion

从意图真实性、问题清晰度和可检索性判断 Query；不合格项携带原因进入反思重写，而不是直接丢弃。

03

多源并发检索

并行使用官方 API、Web Search、视频平台摘要和图文补偿内容，降低单一信源造成的结果分布偏差。

04

清洗与实体识别

对原始结果去噪、去重、抽取正文，并识别品牌与竞品实体，形成统一证据集合供后续回答与评价。

05

三维评估

同时计算引用链接重合度、答案语义相似度和品牌实体识别率，避免单一文本相似度掩盖信源错误。

06

漂移检测

将真实 App 结果作为动态基准，按历史趋势识别平台算法变化，并反馈调整 Prompt、检索来源与权重。

05 / ENGINEERING DECISIONS

关键选择都围绕“更像真实用户”展开。

多源补偿而非单 API

仅使用开放 API 更稳定，但无法覆盖 App 的短视频信源偏好。

加入视频摘要和图文转化内容，以更高检索复杂度换取跨信源一致性。

LLM 质量门控

规则校验便宜，但难以判断口语表达是否符合真实搜索意图。

使用 Judge 给出语义级判定，并让 Reflexion 消化失败原因后重写。

三维指标

只看答案语义相似度实现简单。

加入引用链接和品牌实体维度，使评估能区分“说得像”和“证据真的一致”。

活体 Ground Truth

固定测试集方便复现，但无法跟随 App 更新。

持续采集真实 Query-Response，并用历史窗口控制波动，兼顾可比性和时效性。
