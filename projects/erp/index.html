01 / OVERVIEW

业务复杂度来自跨域协同，而不只是增删改查。

系统同时处理库存扣减、业务单号、租户隔离、项目工时审批和企业微信身份同步。开发重点是保证并发写入的一致性、异步链路中的租户上下文、流程与业务状态最终一致，以及多企业主体接入时的 Token 和回调可靠性。

CONSISTENCY

库存存在并发竞争

采用 MySQL 条件 UPDATE 与 InnoDB 行锁完成原子扣减，通过受影响行数判断库存是否充足。

TENANCY

隔离逻辑容易遗漏

MyBatis Plus 拦截器自动注入 tenant_id，并为全局、表级和注解级场景提供受控豁免。

WORKFLOW

流程和业务状态可能分叉

监听流程实例与任务节点事件，把工时业务键和流程实例双向绑定，并处理驳回重提与重复提交。

INTEGRATION

多 Corp 接入状态复杂

统一管理多个 WxCpService，Redis 共享 AccessToken，并对通讯录、审批附件和消息回调做幂等处理。

02 / RESPONSIBILITY

负责库存、租户、流程与企业微信关键链路。

01

库存与单据号

实现 SQL 原子扣减和库存不足判定；使用 Redis INCR 与按日 TTL 生成 14 类可读、唯一的业务单据号。

02

多租户上下文

实现 TenantLineHandler 自动隔离，并将 Tenant 上下文传播到定时任务、子线程和消息 Header。

03

工时审批状态机

完成业务与 Flowable 实例双向同步、驳回修改重提、三元组幂等校验和异常流程清理。

04

企业微信接入

实现多 Corp 服务管理、OAuth2 登录、通讯录 8 类事件、审批附件下载、软禁用与消息去重。

03 / ARCHITECTURE

业务写入、流程状态与外部事件统一收敛到领域服务。

Web 和企业微信请求经过身份与租户上下文进入业务服务。库存和财务写入依赖数据库原子性，工时业务与 Flowable 双向同步，异步任务和消息消费显式恢复 Tenant 上下文。

04 / CORE MODULES

四条业务主线中的关键工程实现。

01

库存原子扣减

使用 count = count - N WHERE count >= abs(N)，由 InnoDB 行锁保证单条 UPDATE 原子性，受影响行为 0 即库存不足。

02

业务序列号

Redis Key 按业务前缀和日期组织，INCR 生成 6 位序号并设置按日过期，覆盖采购、销售出库等 14 类单据。

03

租户自动隔离

TenantDatabaseInterceptor 为 TenantBaseDO 表自动追加 tenant_id，并提供 ignore-tables 与 @TenantIgnore 等豁免层级。

04

异步上下文传播

@TenantJob 与 AOP 遍历租户执行定时任务，消息消费者从 Header 提取 tenant_id，避免 ThreadLocal 在异步边界丢失。

05

工时流程同步

流程实例级与任务节点级监听器协同更新业务状态，保留同一工时周期的流程实例并支持驳回修改重提。

06

多 Corp 微信接入

ConcurrentHashMap 管理多个 WxCpService，Redis 共享 Token；通讯录删除采用软禁用并发布领域事件清理关联。

05 / ENGINEERING DECISIONS

优先使用已有一致性边界，减少不必要的分布式复杂度。

数据库原子性

为库存扣减额外引入 Redis 分布式锁会增加网络往返和锁续期问题。

单条条件 UPDATE 已由 InnoDB 行锁串行化，因此直接使用受影响行数表达业务结果。

共享库多租户

每租户独立数据库隔离更强，但运维和跨租户汇总成本更高。

采用 tenant_id 自动注入，并对集团汇总表提供经过评审的显式豁免。

驳回后复用流程

重新发起流程实现容易，但会产生冗余实例并破坏工时周期追踪。

定位当前驳回任务后编程式恢复审批，保持流程实例 ID 不变。

删除用户软禁用

通讯录删除回调直接物理删除会破坏历史审批和工时关联。

先禁用账号并发布事件清理活跃项目成员关系，保留历史审计数据。
